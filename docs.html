Before you test

Confirm the firmwareUse the firmware shown in PS4 system information. Do not guess or select a different version to force a route.
Record the console modelOriginal, Slim, or Pro. This makes reports comparable.
Disable autoloadBegin manually. Autoload has a cancel window and disables after three unfinished launches, but research testing should remain manual.
Close other workSave anything important. Browser crashes, freezes, and reboots are possible during research testing.
Use only hardware you own or are authorized to test. Do not install unknown payloads, substitute offset tables, or treat social-media claims as verified support.

How to test the 13.02 research path

1. Start from the main page.

Open NEXT on an actual PS4. Confirm that the detected firmware reads 13.02. If it does not, stop; the 13.02 test must not be forced.

2. Keep the run manual.

Do not enable autoload and do not select a payload. Choose Run 13.02 Research. The separate research page should identify itself as an isolated SlopKit userland test.

3. Run one attempt.

Choose Run SlopKit Userland Test once and wait for a terminal status. Do not rapidly retry. Record the last stage shown, whether the page returned, and whether the browser, application, or console crashed.

4. Stop after instability.

If the browser stalls, freezes, or reboots, do not loop the test. Reopen Safe Recovery, then capture the diagnostics and submit one report.

5. Preserve the evidence.

Open Diagnostics before clearing host data. Download the full JSON report and note the exact action and visible stage immediately before the result.

What the result means

ObservationInterpretation
Userland test succeedsUseful WebKit/userland evidence only. It is not a kernel exploit.
Browser or application crashA reproducibility signal. It does not prove kernel control.
Freeze or rebootReport as observed behavior or “possible kernel panic” only when that is genuinely what happened. Do not label it a kernel exploit.
Kernel fields remain “NOT VERIFIED”Expected. The public 13.02 research page contains no kernel execution path.
GoldHEN remains “LOCKED”Expected. The 13.02 research path does not load a payload.
Evidence standard: a genuine 13.02 kernel result needs reproducible, independently reviewable proof of a kernel primitive or controlled kernel behavior. UI labels, a crash, a reboot, or userland arbitrary read/write alone are insufficient.

How to submit a useful test report

  1. Open Diagnostics after the attempt.
  2. Enter an optional tester alias and select the real console model.
  3. Select the actual entrypoint and candidate. For this page use SlopKit unless you knowingly tested something else.
  4. Choose the closest observed outcome. Use the notes for the last visible stage, approximate wait time, number of attempts, and steps needed to reproduce it.
  5. Keep diagnostics included. User-Agent inclusion is optional; review the report preview before consenting.
  6. Download the full report for your records, check the consent box, then submit it to KillerNoS. If the endpoint fails, use the GitHub short-report option and attach the downloaded JSON only if you are comfortable sharing it.

Do include

Exact firmware, console model, build ID, entrypoint, candidate, last successful stage, exact outcome, retry count, and whether Safe Recovery was needed.

Do not include

Passwords, account identifiers, IP addresses, private keys, purchased content, copyrighted system files, or unrelated personal data.

Troubleshooting and recovery

  • Wrong firmware detected: stop and report the displayed firmware and User-Agent. Never override the check to force a runtime.
  • Repeated unfinished launches: the host disables autoload after three. Use Safe Recovery and return to manual testing.
  • Cached old build: open Safe Recovery, clear host settings if needed, then reload NEXT while online.
  • Report endpoint unavailable: download the full report and use the GitHub short-report fallback.
