Getting Started

Use the normal NEXT host first and confirm the firmware shown by the page matches the console. Firmware routing is intentionally separated: 12.00 uses the established runtime path, 13.00 is treated as a comparison/compatibility baseline, and 13.02 through 13.52 are isolated research targets.

Research mode is observational. A changed result, interruption, crash, or source match does not by itself prove a vulnerability, kernel primitive, exploit, or jailbreak.
1. Confirm firmware

Use the detected PS4 user agent result. Query-string or manually entered firmware values are simulation only.

2. Open research mode

For 13.02–13.52, use the isolated research route rather than a production kernel/HEN path.

3. Run safe comparisons

Collect browser-visible environment, API, storage, buffer, route, and runtime observations.

4. Export results

Keep the local export so results can be compared without changing runtime state.

Testing Firmware 13.02+

The 13.02, 13.50, and 13.52 research paths are for bounded, non-destructive browser-visible observations. Use 13.00 as the nearest comparison baseline when possible.

  • Run a small repeated session rather than an unbounded stress test.
  • Record whether the result is stable, variable, erroring, or inconclusive.
  • Do not treat timing differences alone as a meaningful behavior change.
  • If a previous run stopped unexpectedly, record it as an interrupted run only.
  • Reproduce meaningful differences independently before moving them into the review queue.

Stable test IDs include environment, user-agent/platform, API availability, network state, route/runtime mode, reversible storage, Worker/Blob availability, typed arrays, ArrayBuffer/DataView, timing API, and runtime readiness checks.

Submitting Research Reports

A useful report should identify what was tested and what was observed without including personal information.

Include

Firmware detected, firmware source, test-suite version, test ID, stage reached, result, return value/type where relevant, exception name/message, elapsed time, visibility/network state, whether the previous run was incomplete, evidence class, and notes.

Do not include

Real name, PSN name, email address, console serial, MAC address, or other unnecessary identifiers.

Hardware evidence should only be labeled HARDWARE_OBSERVED when the firmware was detected from the actual PS4 user agent and the result was not simulated, imported, query-derived, or manually entered.

Understanding Research Results

Comparison results use conservative labels such as SAME, CHANGED, MISSING, NEW, ERROR, INCONCLUSIVE, and EXPECTED.

Research evidence is kept separate from conclusions. SIMULATED means the environment was simulated, SOURCE_CONFIRMED means a public source supports the claim, and HARDWARE_OBSERVED means the observation came from qualifying hardware provenance.

Review states describe how much observational follow-up has happened. Reproducing a browser-visible difference means only that the difference was reproduced; it does not promote that result into a kernel or exploit claim.

Source correlation is documentary only. A strong public-source match can help explain an observed difference, but it never converts public documentation into hardware evidence.

For 13.02–13.52, kernel exploitation, HEN, GoldHEN, and payload execution remain outside the research-mode claim unless separately and independently verified.
